# Security

The webview is **untrusted**, and DuckDB SQL can reach the filesystem and network (table functions,
`ATTACH`, extensions, `COPY`). The plugin layers two independent gates, both checked before the
backend touches DuckDB:

1. **Tauri capabilities / permissions** — which commands the webview may invoke at all.
2. **Scope entries + the Rust `Policy`** — which values (connections, paths, statements, extensions)
   those commands may use.

## Permissions (capability files)

Each command has autogenerated `allow-<command>` / `deny-<command>` permissions, plus two sets:

- `better-duck-tauri:default` = `allow-load` + `allow-close` + `allow-select`. Read-only: opening a
  connection and running `select`. **Writes and raw SQL are not included.**
- `better-duck-tauri:allow-raw-sql` = `allow-select` + `allow-execute`. Umbrella for arbitrary SQL;
  a capability must opt in explicitly.

Grant writes with `better-duck-tauri:allow-execute` (and `allow-import`/`allow-export`/
`allow-append_rows`/… as needed). Example:

```json
{
  "identifier": "duck",
  "windows": ["main"],
  "permissions": [
    "better-duck-tauri:default",
    "better-duck-tauri:allow-execute",
    { "identifier": "better-duck-tauri:allow-load",
      "allow": [{ "connection": "duckdb:analytics.db" }] },
    { "identifier": "better-duck-tauri:allow-import",
      "allow": [{ "path": "data/" }] }
  ]
}
```

## Scope entries

A capability can attach a `scope` of `Entry` objects to constrain command arguments. Each `Entry`
has two optional fields (camelCase in JSON):

- `connection` — allow a connection string (checked by `load`).
- `path` — allow a filesystem path prefix (checked by `import` source and `export` target).

Enforcement is **per field** and **deny-first**:

- A matching **deny** entry always rejects.
- If any **allow** entries exist *for that field*, the value must match one.
- An **empty** allow list for a field means that field is **unconstrained** by the capability (the
  init-time `Policy` is still the mandatory layer). Consequence: a capability declaring only `path`
  entries does not restrict `connection`, and vice-versa — populate both to constrain both.

`connection` matches **exactly**. `path` matches by whole-component prefix and is traversal-safe: a
`..` segment is rejected outright (so `data/` never allows `data/../secret`), and `data` allows
`data/x` but not `database/x`. Backslashes are treated as separators (Windows). The scope schema is
declared in `scope::Entry` and registered from `build.rs`.

Example scope entry allowing one database and one export directory:

```json
{ "connection": "duckdb:analytics.db", "path": "exports/" }
```

## The Rust `Policy` (init-time, mandatory)

Configured on `core::Builder` / `diesel::Builder`. Default is fully permissive — opt into each
restriction. This layer applies to every operation regardless of capabilities.

| Builder method | Effect |
|---|---|
| `read_only(true)` | Opens databases `READ_ONLY` and rejects writes (`execute`/`import`/`append_rows`/`revert`) |
| `allow_connection(s)` | `load` accepts only these exact connection strings (repeatable) |
| `allow_path(dir)` | import/export paths must resolve within one of these directories (repeatable; canonicalized, prefix-checked) |
| `deny_risky_statements(true)` | Rejects risky leading keywords in `select`/`execute`/`export`/`explain` |
| `allow_network(true)` | Allows loading network extensions (`httpfs`/`aws`/`azure`); **off** by default |

`deny_risky_statements` rejects statements whose leading keyword is one of: `ATTACH`, `DETACH`,
`INSTALL`, `LOAD`, `PRAGMA`, `COPY`, `SET`, `CALL`, `EXPORT`, `IMPORT`. It is a coarse,
**leading-keyword-only** filter.

`load_extension` is gated by `check_extension`: when `allow_network` is off, the network extensions
`httpfs`, `aws`, `azure` are rejected (they enable SQL-driven network egress / SSRF / exfiltration).

Policy errors surface as `Error::Denied(...)` ("denied by policy: …") to the webview.

## The `select` caveat — read this

`select` is in the default permission set, but DuckDB `SELECT` can still reach the filesystem through
table functions (`read_csv_auto`, `read_parquet`, `glob`, …). The `deny_risky_statements` filter only
inspects the **leading keyword**, so a `SELECT ... FROM read_csv_auto('/etc/passwd')` passes it.

For an untrusted webview, treat `select` as filesystem-read-capable and defend in depth:
- `read_only(true)` plus a `allow_connection(...)` allow-list, and/or
- a capability scope that pins `connection`,
- keep `allow_network(false)` so network extensions cannot load.

A fully sandboxed read-only mode (disabling DuckDB external file access) is a planned follow-up.

## Safe defaults checklist

- Start from `better-duck-tauri:default`; add `allow-execute` only where writes are truly needed.
- `read_only(true)` for any connection the webview only reads.
- `allow_connection(...)` + a scope `connection` entry to pin which databases open.
- `allow_path(...)` + a scope `path` entry for import/export directories.
- `deny_risky_statements(true)` to block `ATTACH`/`INSTALL`/`COPY`/… via `select`/`execute`.
- Leave `allow_network(false)` unless a feature genuinely needs `httpfs`/`aws`/`azure`.
